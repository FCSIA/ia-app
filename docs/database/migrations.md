## What Is a Migration?

A **migration** is a versioned file that describes a change to the database structure. Every time you modify `schema.prisma`, you create a migration so the database can be updated to match.

Think of migrations as a history of every change ever made to the database structure. This means:
- You can reproduce the exact database on any machine
- You can see what changed and when
- Changes are applied in order, consistently

---

## Migration Files

Migrations live in:
```
apps/api/prisma/migrations/
└── 20260302224513_init/
    └── migration.sql
```

The folder name includes a timestamp and the migration name. The SQL inside is generated by Prisma — never edit it manually.

---

## Commands

### Create and apply a migration (development)
```bash
pnpm db:migrate
# or with an explicit name:
pnpm --filter api exec prisma migrate dev --name add_user_email
```

This:
1. Compares the current `schema.prisma` to the current database state
2. Generates a new SQL migration file
3. Applies it to the database
4. Regenerates the Prisma client

### Apply existing migrations (on a new machine)
When you clone the repo, the migration files already exist. Run:
```bash
pnpm db:migrate
```
Prisma sees the migration files, checks which ones have been applied to this database, and runs any that haven't been.

### Apply without generating new migrations (production)
```bash
pnpm --filter api exec prisma migrate deploy
```
Only applies existing migration files — doesn't create new ones. Used in production.

## The Init Migration

This project has a single migration: `20260302224513_init`. It creates all tables at once because the entire schema was designed upfront.

The SQL inside creates all 23 tables, enums, indexes, and foreign key constraints.

---

## Making Schema Changes (Workflow)

1. Edit `apps/api/prisma/schema.prisma`
2. Run `pnpm db:migrate` — Prisma generates the diff and migration file
3. The new migration is applied to your local database
4. `pnpm db:generate` runs automatically (or run it manually)
5. Commit both `schema.prisma` and the new migration file to git

Other developers pull your changes and run `pnpm db:migrate` — they get the same database state.

---

## Prisma Shadow Database

During `migrate dev`, Prisma creates a temporary "shadow database" to calculate the diff safely. This requires your database user to have `CREATEDB` permission:

```sql
ALTER USER ia_user CREATEDB;
```

This was already done during setup.
